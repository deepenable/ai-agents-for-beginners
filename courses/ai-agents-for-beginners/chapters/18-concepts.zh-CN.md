# 用签名收据区分完整性、身份与授权

## 学习目标

本章面向已了解工具调用、人工审批和审计需求的学习者。完成后，你应能解释一张收据究竟证明了什么，并设计“批准了这个动作”与“代理报告执行了这个动作”的可验证连接。

- 区分日志、哈希、签名、加密和身份认证。
- 解释 JCS 规范化、Ed25519 直接签名、内容摘要与收据链。
- 识别嵌入公钥、可信公钥注册表、审批人和代理权限的差别。
- 用篡改、重放、过期授权、密钥轮换及摘要替换反例检验设计。

## 步骤一：从“记录了”追问到“谁可信”

普通日志方便调试，但拥有写权限的人可能改写记录。哈希能帮助核对内容，却不能单独识别谁作了承诺，因为任何人都能重新计算哈希。

数字签名让持有可信公钥的验证者核对签名与内容是否匹配。它仍依赖公钥来源：收据内自带的公钥只能验证数学关系，不能自动证明该钥匙属于某组织或审批人。

| 机制 | 能提供什么 | 不能提供什么 |
| --- | --- | --- |
| SHA-256 摘要 | 以固定长度绑定某组字节 | 签名人身份、保密、动作正确性 |
| Ed25519 签名 | 对相应公钥的签名关系和内容完整性 | 自动识别真实人、阻止合法私钥持有人说谎 |
| 可信密钥注册表 | 将批准的公钥与权限范围连接 | 保证审批界面诚实、密钥从未失窃 |
| 动作审批收据 | 在约束满足时绑定精确动作与批准声明 | 保证下游支付确实成功或现实结果正确 |
| 外部锚点/可信时间 | 为已知链头提供额外时序证据 | 自动补齐未记录的事件 |

“密码学收据”不是加密文件。签名后的 JSON 仍然可读；摘要也不是匿名化技术，低熵参数可被枚举推测。真实参数应按隐私要求另外保护，审批收据中的完整 action 尤其需要访问控制。

## 步骤二：明确签名的字节边界

基础 notebook 零基单元格 5 定义编码与哈希辅助函数；11 的 `sign_receipt` 直接签名 JCS 规范字节：

```python
canonical = canonicalize(payload)
signature_bytes = signing_key.sign(canonical).signature
```

随后将 `signature = {"alg", "sig", "public_key"}` 附加在平铺 payload 外。验签时去掉整个 `signature` 对象，再把同样的 JCS 字节交给 `VerifyKey.verify`。不要把签名本身放入被签 payload 造成循环。

JCS 对 JSON 的数字、字符串和对象排序有具体规范，不等于任意 `json.dumps(sort_keys=True)`；两种实现只有对同样的规范对象才可得到一致字节。

SHA-256 在这里有两个不同用途：

1. `sha256_canonical(tool_args/result)` 把参数和结果绑定到 payload 的摘要字段。
2. `receipt_hash` 对**包含 signature 的完整收据**规范化后求哈希，用作链连接。

**不在签名前额外计算 `SHA-256(JCS(payload))`。** Ed25519 本身按其算法处理消息；额外预哈希改变了协议输入。单元格 13 的 `prehashed_receipt` 就是负对照，应不能通过直接 JCS 验证器。

源码使用 `alg="EdDSA"`，实际密钥算法为 Ed25519。把字符串改成其他算法名不会自动提供新算法实现，尤其不能靠标签获得后量子安全。

## 步骤三：分开验证单张与整条链

基础 notebook 单元格 19–23 构造 `lookup_flights → hold_seat → confirm_booking` 三张模拟收据。每张包含序号和上一张完整收据的摘要。

`verify_chain` 检查三件事：当前签名有效、前驱摘要吻合、序号等于数组下标。篡改中间收据时：

- 第 0 张不受影响。
- 第 1 张的签名失配。
- 第 2 张的签名仍可能正确，但前驱摘要与改动后的第 1 张不符。

链完整性失败不等于“后面所有单独签名都失效”。删除或重排会破坏邻接/序号；但是删除末尾得到一个原本有效的前缀，当前验证器仍可能接受。若要检测截尾、回滚或整条链重写，需要预先可信的最终长度、链头摘要或外部锚点，不能只检查手里剩下的链。

时间戳是被签署的声明，不天然是可信时钟证明；顺序是所提交链中的逻辑关系，不证明所有现实动作都被记录。

## 步骤四：把人工批准绑定到精确动作

人工授权 notebook 使用两个独立密钥集合 `APPROVER_KEYS`、`AGENT_KEYS`，同一个 `verify_envelope` 按类型选择不同可信注册表：

| 对象 | 主要字段 | 权威来源 |
| --- | --- | --- |
| `human.approval.v1` | 完整 `action`、`action_digest`、审批人、策略版本、签发和过期时间 | 审批人注册表 |
| `agent.action.v1` | 完整 action、同一摘要、`parent_approval_ref`、运行号和结果声明 | 代理注册表 |

`key_id` 是查找提示，不是收据自己授予的权限。用另一把钥匙签名但冒用已固定的 key ID，会被验签拒绝；把一个未知 key ID 写进收据也不能添加信任。

单元格 8 的 `verify_chain(action_being_executed, approval, agent_rcpt, now)` 顺序检查：

1. 两种收据的类型、结构和各自可信签名。
2. 两张收据的完整 action 与摘要均等于当前动作。
3. 动作收据指向的 `parent_approval_ref` 等于完整批准收据的哈希。
4. 策略版本仍是当前版本，批准没有过期。
5. 批准引用还没在 `_consumed` 集合中使用；成功后登记消费。

这让“改金额”“拿动作 A 的批准执行动作 B”“使用过期批准”“轮换后旧钥匙继续批准”“同一个批准重复执行”得到可区分拒绝原因。签名仍有效的批准也可能已经失去权限。

## 步骤五：把教学保证与真实系统保证分开

人工授权示例中的审批人字符串带有 WebAuthn 字样，但代码实际只生成 Python 内存密钥，**没有 WebAuthn、真实审批 UI 或人机认证**。`execute` 返回 `"executed"`，不调用银行或退款系统；收据的 `outcome="performed"` 是示例声明，不是下游实际效果的独立证据。

还要认识这些局限：

- `_consumed` 是进程内集合；重启丢失，多进程不共享，也没有事务原子性。真实系统要在执行前以持久状态原子消费批准，并配合幂等动作。
- 时间使用统一 UTC 字符串比较；源码没有完整时间格式解析、可信时钟、未来签发和执行时间一致性验证。
- 策略版本相同不代表真的评估了政策，审批人标签与密钥归属仍需身份基础设施。
- 结构与错误处理涵盖提供的反例，不是对任意恶意输入的完整模式验证器。
- 基础 `ReceiptedTool` 在同步函数正常返回后才签名；函数抛异常时不会生成失败收据，多个 wrapper 也各有独立内存链。

因此合适的结论是：“在固定密钥、给定时钟、模拟动作和指定检查下，两个签名声明被绑定到同一规范动作。”不能推广为“真实人确实看见并批准了全部内容，真实退款只执行一次且效果正确”。

## 步骤六：选择生产加固方向

基础演示构造平铺 payload 加 signature，不是相关 IETF Internet-Draft 的 `{payload, signature}` wire format；人工审批类型也是本课程的教学组合，不是草案定义类型。使用 Ed25519/JCS 原语不等于已通过第三方格式一致性测试或满足法规。

未来加固应包括：

- 私钥由支持所选算法的受保护签名设施管理，核查具体 Key Vault/HSM 支持，不能假设任意云密钥服务直接支持当前调用。
- 通过认证渠道发布公钥、绑定主体与用途，制定轮换、撤销和历史验证政策。
- 不可变/追加式存储与外部链头锚定，防止截尾、回滚和重写；明确保留期与审计者如何取得预期链头。
- 需要选择性披露时设计字段级承诺与证明路径；简单拼接两个收据的哈希只是入门承诺练习，不自动成为完整 Merkle 证明。
- 探索执行前/执行后分签、跨实现测试向量与后量子双签迁移时，先定义格式和验证器再更换算法标记。

## 预期结果与故障排查

完成后应能给每种反例选择正确失败层：签名不匹配、前驱不匹配、摘要替换、策略过期、密钥不可信、批准过期或已消费。

- **合法夹具验不过**：先查是否误用了旧翻译的预哈希路径，再查 JCS、base64url 和签名范围。
- **换公钥后也能验过自己的收据**：这是嵌入公钥验证器的信任边界，不是证明攻击者具有组织授权；切换可信注册表。
- **去掉链尾还通过**：缺少外部预期链头/长度，不能指望单向哈希链发现未知尾部。
- **输出 executed 就当退款成功**：源码只是模拟；需要业务系统回执、幂等与一致性设计。
