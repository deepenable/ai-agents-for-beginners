# 以人为中心设计可理解、可控制的智能体

## 学习目标与准备

本章把两组内容连接起来：源课程的人本设计原则，以及当前 Python 样例的清晰指令、结构化输出和单一职责模式。完成后，你应能把“透明、可控、一致”改写成具体交互要求，并用代码与测试说明哪些要求已经实现、哪些只是提示中的愿望。

建议先读[框架与会话](02-concepts.zh-CN.md)，理解工具、状态与模型输出的区别。本章不需要云账号；活动使用虚构旅行需求。若查看或运行源码，按[环境准备](00-setup.zh-CN.md)采用 Windows、PowerShell 7、Python 3.12+ 及固定版本依赖。平台不会执行手册里的代码。

## 为什么设计原则先于架构

生成式输出具有不确定性，工程师不能仅用“它能回答多少问题”评价体验。智能体应该扩大人的能力、弥补知识空白、支持符合用户习惯的协作，并帮助用户成长，而不是让人失去判断与选择权。

头脑风暴、翻译、任务辅助或生活规划等场景，都可以体现这些价值；但情绪辅导等敏感场景还需要清晰的专业边界。人本原则不是固定软件架构，也不能替代医学、法律或高风险业务的专业审查。

## 空间：连接人、事件和可行动知识

### 连接，而非压缩掉人的参与

旅行智能体可以把用户偏好、候选目的地与人工顾问连接起来，帮助用户比较，而不是隐藏选择、替用户作出未经授权的决定。多人协作时，应让参与者知道哪些信息被共享、由谁负责下一步。

“减少操作步骤”不等于“省去确认”。查询库存可以自动进行，但付款前要展示金额、币种、乘客、日期及退款条件，让用户有真正的修改或取消入口。

### 容易发现，也能适度退到后台

授权用户应在适合的设备上找到智能体；界面可以支持文字、语音、图片等输入输出。前台与后台、主动建议与被动响应应按用户需要切换。

后台运行不等于不可见。用户仍要知道任务是否执行、访问过哪些工具、是否与其他智能体交换信息，以及如何停止它。本课 notebook 只有文本交互，未实现跨设备、多模态或后台控制面板；这些属于可据此评审的产品要求。

## 时间：过去、现在和未来

### 过去：理解历史的状态和语境

历史不只是事件列表，还包含当时的预算、同行人、季节和选择原因。用户上次选择便宜酒店，不代表永远拒绝舒适住宿。智能体可以使用已授权历史改善相关性，但必须允许查看、修正和遗忘，避免把一次行为固化成标签。

### 现在：提供合适的提示，而不是打断

有用的提示把当前状况和可行动选项联系起来。例如“本次预算不足以覆盖这个方案，可减少天数或更换目的地”，比重复推送“预算超出”更有帮助。

提示还需考虑环境、文化、语言、无障碍需求和用户意图。应渐进披露复杂信息：先给核心结果，再提供可展开的细节，而不是一次输出所有工具日志和长篇解释。

### 未来：适应用户，而非无约束地变化

系统可以随着反馈调整风格、偏好和交互方式，并适配不同设备。但用户需要知道哪些偏好被改变、改变作用于哪段时间、如何恢复默认。连续交互塑造体验，不等于模型自动训练或系统拥有无限自主性。

## 核心：承认不确定性，同时建立信任

信任不是靠自信措辞获得的。用户应始终能区分系统正在工作、等待确认、已停止或发生错误；知道 AI 参与了哪些步骤，并有反馈渠道。

对不确定性应给出可操作说明：“此价格来自演示字典，非实时报价”“签证要求尚未核实”“未获得库存信息”。不要把一般模型知识包装成已查询事实，也不要因为输出是合法 JSON 就称其可信。

## 三条实施准则

| 准则 | 旅行产品中的实现要求 | 可验证的反例 |
| --- | --- | --- |
| 透明度 | 明示 AI 身份、示例输入、使用限制；展示调用摘要、历史与反馈入口 | 只说“我已确认”，没有工具或数据证据 |
| 控制 | 可修改偏好、风格、详细程度和任务范围；能停止、查看及删除数据 | 声称已忘记，实际数据库和云端日志仍保留 |
| 一致性 | 跨设备采用熟悉图标和相同状态含义，保持相似动作的响应结构 | 同一个按钮一处表示“建议”，另一处直接“付款” |

熟悉的麦克风、回形针和图片图标能降低认知负担，但图标本身不能代替无障碍标签或权限提示。透明也不是展示模型私有的逐步思维；通常应展示可核验的调用、证据来源、简短理由及不确定性。

## 将原则落实到当前 Python 样例

### 模式一：清晰指令

`TravelConcierge` 的指令定义姓名、语气、预算与活动偏好、先查可用性、给出个性化建议并提到签证和季节。这说明好的指令至少要回答：

1. 角色是谁，适用范围是什么？
2. 必须完成哪些职责，何时应该追问？
3. 不允许做什么，信息缺失时如何回答？

但当前这个智能体没有注册任何工具，虽然指令要求检查可用性，代码并未给它查库存能力。这正好用于评审：**提示要求不等于实现事实**。签证与票价也没有权威数据源，不能作为出行决策。

### 模式二：结构化输出

源样例用 Pydantic 定义机器可读结果：

```python
class DestinationRecommendation(BaseModel):
    destination: str
    available: bool
    best_season: str
    highlights: list[str]
    estimated_budget_usd: int
```

外层 `TravelRecommendations` 包含推荐数组和 `personalized_note`。实际运行传入：

```python
options={"response_format": TravelRecommendations}
```

这把输出格式交给模型与框架进行结构化处理，程序再读取 `response.value`。类型验证能发现字段或形状问题，但当前模型没有约束推荐数量、预算非负、季节格式或目的地必须在字典中。因此还要做业务验证。

例如 Cape Town 的数据是 `available=False`。包含它并明确说明不可预订，与把它标成可预订，是不同的质量结果。合法的 `bool` 不能证明该布尔值来自正确的数据。

### 模式三：单一职责与交接

`DestinationExpert` 负责按偏好检索目的地、查可用性并给简短排序；`LogisticsPlanner` 负责逐日行程、交通酒店建议、签证和保险注意事项。后者没有航班、酒店或政策工具，因此这些内容仍属于待核实建议。

样例把第一位智能体的文本嵌入第二位的请求，是显式串行协作。它没有自动共享所有历史、执行预订或进行独立事实核验。职责分离让测试更清楚，但交接必须保留预算、日期、可用性和用户选择，否则第二位可能丢失约束或擅自换目的地。

## 可选 .NET：从交互原则观察差距

实际 C# 源文件比对应说明文档更具体：包含 `GetRandomDestination` 和 `SaveUserPreference`，以三轮交互展示问候、偏好设置和推荐。`SaveUserPreference` 只是打印日志并返回确认文本，并未写数据库。因此“我会记住”只能结合当前会话理解，不能视为持久化或删除能力。

C# 说明文档还介绍工厂、构建器、策略、命令、观察者、适配器、依赖注入、SOLID、分层架构、日志、缓存、健康检查和扩展性。它们是后续工程设计方向，不是本例全部实现。可以这样理解：

- 创建型模式让不同智能体用一致配置构造；依赖注入便于替换客户端与工具。
- 行为型模式组织执行策略、命令和事件；可用于实现审批、取消和审计。
- 结构型模式隔离外部接口、包装监控和缓存；不能仅凭调用链就宣称已实现生产治理。
- 单一职责、接口隔离与依赖倒置支持测试，但线程安全、负载管理和恢复仍需专门验证。

主线不要求搭建企业基础设施。

## 活动：将原则改成验收用例

1. 为旅行顾问写开场白：明确 AI 身份、只能使用演示资料、不能代订、可随时停止，并给一个输入例子。
2. 设计一次偏好修改：“从豪华旅行改成预算有限的文化旅行。”分别写出需要确认的内容、会话内修改范围和持久化前的授权要求。
3. 为 `TravelConcierge` 找一项“承诺大于能力”的要求，并用“需要新增什么工具，或删除什么承诺”两种方式各写一个修复方案。
4. 阅读结构化字段，制定两条类型规则和两条业务规则。例如字段是整数属于类型规则；可用推荐总预算不得超过用户上限属于业务规则。
5. 设计交接表，至少含目的地、可用性、预算、数据来源和未核实事项；用它检查目的地专家与行程规划者的责任是否重叠或遗漏。

### 预期结果

应得到至少一个透明度、控制和一致性的测试用例，并为每项写明观察证据。不能以“回答看起来专业”代替通过条件；“已删除偏好”必须能检查相应存储，不可只检查智能体的承诺文字。

## 故障排查与风险

| 设计失败 | 改进方向 |
| --- | --- |
| 人设很清晰，却编造实时库存 | 添加受控检索工具，或明确当前无法核实；测试工具调用证据 |
| Pydantic 接受结果，预算仍错误 | 增加业务校验，将结构有效与事实正确分开记录 |
| 第二位智能体忘记预算 | 检查交接文本是否包含预算；使用更明确的交接契约 |
| 提示要求确认，但操作仍自动执行 | 在工具执行层实现审批；提示词不等于安全边界 |
| 用户请求遗忘，只清了内核 | 分别核对会话、数据库、文件、服务端保留策略和日志 |

本章活动没有模型费用和资源创建。不要用真实隐私偏好或敏感出行资料做评审。后续运行多角色样例会多次调用模型；如果接入持久存储、个人偏好和写操作，必须先获得相应数据授权和预算。删除历史不可逆，应先让用户确认作用范围，而非直接删除共享数据。
