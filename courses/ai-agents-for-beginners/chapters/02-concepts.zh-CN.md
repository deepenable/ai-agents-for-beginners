# 选择框架与服务：理解客户端、工具和会话

## 学习目标与准备

学完本章，你应能把旅行智能体拆成可替换的客户端、智能体、工具和会话四层；解释 MAF 与 Foundry Agent Service 为什么可以一起使用；为原型、企业集成和多轮交互选择合适的方案。你还要能指出“在当前会话里适应偏好”与“在线训练模型”的区别。

建议先阅读[智能体基础](01-concepts.zh-CN.md)。本章设计活动只需纸笔，不运行云服务。源码阅读与后续执行以[环境准备](00-setup.zh-CN.md)的 Windows、PowerShell 7、Python 3.12+ 为目标，采用固定源提交和核心依赖 `agent-framework-core==1.10.0`。平台只负责展示手册。

## 从一般 AI 功能到智能体框架

传统 AI 集成可以提供个性化推荐、自动回答常见问题、语音识别或预测输入。它们改善应用体验，但未必会规划任务或与外部系统反复交互。

智能体框架进一步处理三类问题：

- **协作与协调**：多个角色交换结果、分派任务、共同解决问题。框架提供组合方式，团队仍须规定交接格式与冲突处理。
- **多步骤任务管理**：某一步的工具结果会影响下一步。相比单次生成，需要处理调用链、异常、重试和停止。
- **上下文适应**：用户改变偏好或环境改变时，系统要结合已有状态重新选择行动，而不是每次从零回答。

框架的价值是复用这些工程组件，让团队把精力放在业务工具与验收规则上；不是让一个没有数据、权限或业务规则的系统自动成为可靠服务。

## 四层架构与责任边界

### Client：连接与身份

客户端处理认证、请求格式和响应解析。主线的 `FoundryChatClient` 使用项目端点及部署名，Python 变体的 `OpenAIChatClient` 直接使用 Azure OpenAI 资源端点。二者可以共享“定义工具并创建智能体”的思路，但端点、数据权限及远端状态模型不能混用。

凭据对象只负责取得身份凭据，授权由目标服务决定。`AzureCliCredential` 明确使用 Azure CLI 登录身份；`DefaultAzureCredential` 会尝试多种来源，未必选中你刚登录的身份。

### Agent：模型能力加行为契约

当前源码使用 `provider.as_agent(name=..., instructions=..., tools=[...])`。名称帮助区分角色，指令说明职责和限制，工具清单限定可调用能力。部分源 Markdown 仍写 `provider.create_agent()`，本交付以实际代码中的 `as_agent` 为准。

“始终检查库存后推荐”是行为要求，不是库存实现。没有工具和数据，指令本身不能产生真实库存；有工具也仍需观察调用与结果。

### Tools：连接业务边界

工具的函数名、docstring、参数类型和 `Annotated` 描述告诉模型何时使用、输入什么。实际执行逻辑由开发者提供。例如：

```python
@tool(approval_mode="never_require")
def check_destination_availability(
    destination: Annotated[str, "The destination to check availability for"]
) -> str:
    """Check if a vacation destination is currently available for booking."""
```

主线工具读取固定字典，不查询真实订票平台。`destination` 是字符串类型，并不代表所有字符串都有效；大小写和不在字典中的目的地必须纳入测试。

### Session：对话状态，而非用户画像数据库

主线通过 `session = agent.create_session()` 创建状态容器，并将同一个对象传给两次 `agent.run(..., session=session)`。这样第二轮才能使用第一轮的上下文。换成新会话后，不能要求它知道先前的个人偏好。

会话通常含用户输入、工具调用及回答，可能涉及隐私和持续增长的上下文成本。多个用户不能共用一个会话；记录保留、隔离和删除属于产品设计的一部分。

## MAF 与 Foundry Agent Service 的关系

| 维度 | Microsoft Agent Framework | Microsoft Foundry Agent Service |
| --- | --- | --- |
| 定位 | 应用开发 SDK 与组合抽象 | 远端智能体服务及平台能力 |
| 开发者接触点 | Client、Agent、Tools、Session、异步执行 | 项目、模型、智能体定义、服务端状态及工具连接 |
| 适合解决 | 快速原型、定制函数、应用内编排、多个角色 | 企业集成、服务端管理、托管能力与扩展 |
| 仍需负责 | 业务校验、工具安全、测试、生命周期 | 权限配置、数据治理、费用、部署与服务选型 |
| 本模块路径 | 用 MAF 构造并运行智能体 | Foundry 主线作为客户端背后的服务 |

不是“先完全不用 Foundry，等上线再换”。主线 notebook 从第一次连接就使用 Foundry 项目。也不是“使用托管服务后所有工具都在服务器执行”：本例自定义 Python 函数仍在本地运行进程中执行；服务内置检索或代码执行工具有各自的执行位置。

源课程用 Thread、Message、Run 解释对话生命周期：线程保存上下文，消息代表用户、模型或工具的内容，运行表示一次处理过程。当前 MAF 主线把多轮交互暴露为 `AgentSession` 和 `agent.run`。阅读旧的 `create_thread`、`create_and_process_run` 示例时，应理解其概念，但不要混贴进当前 notebook。

## 如何快速原型、迭代与改进

### 模块化：一次只改变一个边界

第一版先使用固定字典，让工具与模型交互跑通；下一版再把字典替换成受控 API。客户端、工具和会话分离，才容易判断失败来自哪个层次。连接器、解析器、提示模板和记忆模块是可复用部件，但只有实际注册的部件才存在于应用中。

例如输入城市名检查失败，先直接检查字典键，再检查模型传给工具的参数，最后才考虑修改提示或模型。不要同时改端点、工具、系统提示和依赖版本，否则很难归因。

### 协作：先定义角色与交接

检索角色负责取得资料，分析角色负责解释资料；规划角色提出步骤，执行角色只能调用获准工具。串行传递前一角色输出是最简单的协作方式，但不自动保证交接内容完整、可信。

源 README 的 `retrieve_tool`、`analyze_tool`、`execute_tool` 属于说明性占位；当前 02 主线没有这些函数，也没有实现完整多智能体协作。它们用于解释职责分配，不作为可直接执行步骤。

### 反馈：把改进变成可检查的闭环

一次交互反馈可以修改当前请求、更新已授权偏好或触发重新检索。要声称长期改进，需记录评价标准、选择哪些反馈、如何更新、如何回滚及如何复测。模型没有因为被告知“我不喜欢”就必然改变权重。

本模块 Azure OpenAI 变体使用 `_last_destination` 避免紧邻两次随机工具调用返回同一城市。这是进程内状态，不是训练，也不是会话级隔离；多个会话共享同一全局变量时会互相影响。

## 企业集成与方案选择

已有 Azure Search、Azure Functions 或其他业务 API，可以通过自定义工具或服务支持的连接方式接入；不必为使用框架重建全部系统。但还要分别处理服务身份、网络访问、租户隔离、数据许可证与审计。

- 需要快速验证一项业务能力：先用单智能体和一个只读工具，减少变量。
- 已有 Azure OpenAI 部署、希望直接调用模型：阅读本模块独立 Python 变体，确认端点与认证。
- 需要项目内智能体管理、知识工具及企业集成：使用 Foundry 主线，并在后续单独评估部署和治理要求。
- 需要多角色协同：先验证单个角色，再定义可机器检查的交接格式；不要把“更多智能体”当作默认优化。

源门户补充材料描述建立 hub、部署模型和创建 `FlightAgent`。菜单属于当时的门户路线，可能不适用于当前项目类型。其示例跳过知识和动作连接，因此只能测试意图理解、追问出发地/目的地/日期及友好错误提示，不能验证实时航班状态。

## 活动：画出两轮查询的状态与数据流

1. 给四层各画一个框，写出本模块实际符号：`FoundryChatClient`、`TravelAvailabilityAgent`、`check_destination_availability`、`AgentSession`。
2. 第一轮询问 Barcelona；沿箭头注明用户消息、工具参数、字典返回值和最终回答。
3. 第二轮说“换一个温暖的地方”。标明会话提供什么信息、工具缺少什么能力。注意：只有“检查某个城市”的工具，没有“枚举所有城市”的工具。
4. 将“主线使用 Foundry”改成“直接 Azure OpenAI”，圈出必须变更的客户端、端点变量及权限，其余结构尽量保留。
5. 写一个新会话对照：第二轮单独出现时应追问或提出假设，不应声称知道第一轮选择。

### 预期结果

流程图应显示工具结果回到模型，而不是模型的函数调用请求直接变成用户最终答案；两轮共享同一个会话对象；未知库存不能被解释成查到了全世界所有目的地。完成后能独立解释“跨轮上下文”和“全局工具变量”的不同作用域。

## 常见误解与排查

| 误解 | 如何纠正 |
| --- | --- |
| MAF 和 Foundry 必须二选一 | 查看主线：MAF 的客户端连接 Foundry，职责位于不同层 |
| 登录成功就拥有所有服务权限 | 分别核对模型推理、项目管理和各工具数据权限 |
| 会话会自动跨进程持久化 | 检查是否有显式存储与恢复；内存对象不能证明持久化 |
| 工具显示“不 available”就是售罄 | 本例未知键也返回不可用，缺少“未知”状态，需要额外解释 |
| 第二次不同推荐证明模型学会偏好 | 先检查是否只是随机函数排除上次值或会话文本生效 |
| 源文提到的企业功能都已实现 | 对照实际函数与资源，示例没有完整监控、缓存或权限治理实现 |

## 费用、权限、删除风险与清理

本章活动不调用模型、不创建资源，也不需要安装新的 SDK。架构演练只使用虚构数据。若进一步选择门户创建资源或连接外部系统，必须先审批模型推理、存储与工具费用，以及项目范围权限；不得为了原型直接授予整个订阅管理权。
